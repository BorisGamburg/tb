# План реализации компенсационного закрытия в Pyramid 2

## 1. Определение Base

Находим базовый уровень в стеке:

- **Buy** — уровень с минимальной ценой входа.
- **Sell** — уровень с максимальной ценой входа.

Base всегда закрывается полностью.

## 2. Расчёт бюджета компенсации

Рассчитываем ожидаемый PnL Base при текущей цене закрытия с учётом:

- цены входа;
- текущей цены закрытия;
- комиссии открытия;
- комиссии закрытия.

Из ожидаемой прибыли Base вычитаем `min_pnl`.

Полученная сумма — **бюджет компенсации в USDT**.

Если бюджет нулевой или отрицательный, компенсационное закрытие не выполняется.

## 3. Поиск убыточных уровней

Для каждого уровня, кроме Base, рассчитываем ожидаемый PnL при текущей цене закрытия с учётом комиссий.

Отбираем уровни с отрицательным PnL.

Сортируем их по убыванию убытка на монету:

1. Самый убыточный уровень.
2. Следующий по убыточности.
3. И так далее.

## 4. Последовательное расходование бюджета

Обрабатываем отсортированные уровни строго по очереди.

Для каждого уровня:

1. Рассчитываем, какое количество монет можно закрыть на оставшийся бюджет.
2. Учитываем `qty_step` и `min_qty`.
3. Не допускаем остатка уровня меньше `min_qty`, если такой остаток не может существовать по правилам биржи.
4. Если даже минимальный допустимый объём закрыть нельзя, пропускаем этот уровень и проверяем следующий.
5. Если бюджета хватает на полное закрытие уровня:
   - закрываем уровень полностью;
   - вычитаем стоимость его погашения из бюджета;
   - переходим к следующему уровню.
6. Если бюджета хватает только на частичное закрытие:
   - закрываем максимально возможное количество;
   - завершаем планирование;
   - к следующим уровням не переходим.

**Важное правило:** нельзя переходить к менее убыточному уровню, если текущий можно закрыть хотя бы частично. Исключение — если минимальный допустимый объём закрытия текущего уровня недоступен.

Если после обработки уровней остаётся небольшой бюджет, которого недостаточно для минимального объёма закрытия ни одного из оставшихся уровней, он не используется.

## 5. Формирование плана закрытия

План содержит:

- Base и его полный объём закрытия;
- список убыточных уровней с рассчитанными объёмами закрытия;
- суммарное количество монет для закрытия;
- ожидаемый итоговый PnL.

Итоговый PnL должен быть не меньше `min_pnl` с учётом комиссий.

## 6. Исполнение

Весь план исполняется **одним общим ордером**.

Объём ордера:

`Base qty + сумма рассчитанных объёмов убыточных уровней`.

В ордер передаются все уровни, участвующие в плане, и соответствующие им объёмы закрытия.

## 7. Учёт фактического исполнения

Планировщик (п. 2-5) и учёт факта - два разных алгоритма. План работает до
ордера и отвечает на вопрос "сколько отправить на биржу", исходя из прогноза.
Как исполнится ордер, заранее неизвестно, поэтому после исполнения объёмы
по уровням из плана не используются.

После исполнения ордера фактически закрытый объём распределяется по уровням
оптимизатором списания (`FillApplier.apply`, он же `writeoff_optimizer`),
так, чтобы получился безубыток (`min_pnl`):

- Исходные данные - только фактические: `exec_result.qty`, `exec_result.price`,
  `exec_result.fee`.
- В оптимизатор передаются только Base и убыточные уровни из плана.
  Прибыльные Extension в расчёте не участвуют.
- Оптимизатор сам решает, с каких уровней и сколько списать. Никакого заранее
  заданного порядка "Base, затем убыточные по плану" нет.
- Если безубыточное распределение невозможно, выбирается вариант с минимальным
  убытком.
- Результат применяется к стеку через `Accounting.reduce_level_2()`.

Распределение факта может не совпадать с планом - это ожидаемо.

## 8. Поведение при неисполнении

- Если ордер не исполнен — уровни не изменяются.
- Если исполнен частично — учитывается только фактически исполненный объём.
- Если исполнен полностью — применяются все запланированные сокращения.

Повторный rearm выполняется только после полного исполнения, согласно существующей логике Pyramid 2.

## 9. Реализация

В качестве отправной точки используем существующий `PyrCompensationPlanner`, но расширяем его с одного убыточного уровня на последовательную обработку нескольких уровней.

Потребуется также адаптировать `PyrRecoveryMode` и `PyrCloseProcessor`, поскольку сейчас они рассчитаны на закрытие Base и только одного убыточного уровня.

При этом отдельно проверим существующие функции распределения частичного исполнения, чтобы не смешивать:
- планирование компенсации по бюджету PnL;
- распределение фактически исполненного объёма.

**Итоговая идея:** полностью закрываем Base, а его прибыль за вычетом `min_pnl` последовательно расходуем на погашение самых убыточных уровней. Всё это выполняется одним ордером с последующим корректным распределением фактического исполнения по уровням.
